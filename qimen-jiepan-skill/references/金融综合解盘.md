# 金融综合解盘

技能0.10.0的新分析工作流。方法 `FINANCE_MULTI_ROLE_V2_CANDIDATE`，版本0.1.0；映射与边界维护于[finance_multi_role.json](../assets/finance_multi_role.json)。这是可留档、可纠偏的综合解盘框架，尚未证明价格预测能力提升。旧F01—F10只作独立基线，不作为新综合结论的必选答案。

## 1. 冻结对象与资料

沿用用户已选原盘，保留问时、盘法、问题、期限与版本。先明确本周/下周的日期，再查交易或估值日历。换时辰不会自动使周盘失效。外部盘无法程序核验时人工读已知字段，注明未核部分，不补造元数据。

产品核对：市场、代码、管理人、份额类别、跟踪指数、目标ETF、币种、价格或净值收益口径及资料日期。ETF联接的名称相似不等于跟踪同一只ETF；同码不同市场也不能混用。来源优先交易所、指数公司、管理人。

将以下信息加在原[产品档案](金融数据与幅度.md)上，未知字段保持未知：

| 字段 | 用途 |
|---|---|
| theme、theme_source | 本方法固定主题及产品对应资料来源；基金/ETF不能仅凭名称或旧sector自动猜主题 |
| exposures | 已核子主题数组：id、theme、source、as_of，可选available_at、weight_pct |
| target_etf | 可选目标ETF档案：id、market、code、name、metadata_source；逐项核对后冻结 |
| valuation_windows | 场外基金逐日采价start/end/source；缺少时仍能解盘，但完整前瞻分类为timing_unverified |
| evaluation_role | prospective或development；已读过行情的开发案例必须用development |
| analysis_conditions | 对具体角色明确绑定的实际空/墓限制；与旧role_context分开 |

主题例：`theme: "ai"`，敞口可分`semiconductor`硬件和`software`应用，各留来源和归属日期。缺权重不编权重，不据此算加权收益；不完整的非重叠敞口可以不满100%，不得重复统计同一成分。程序只保存已提交资料，官方投向真实性还需实际核查。

## 2. 固定角色与全盘主线

| 角色id | 固定对象 | 分析用途 |
|---|---|---|
| market.index | 景门 | 指数行情及热度 |
| market.trend | 值符星 | 大势背景、结构稳定性 |
| market.capital | 天盘戊 | 资金条件 |
| market.profit | 生门 | 利润机会 |
| market.participation | 开门 | 参与和流通条件 |
| market.process | 值使门 | 过程与节奏 |
| market.issue | 原时干，甲按具体时柱遁仪 | 问题背景 |
| product.primary | 已固定的产品主题主象；宽基景门；未定主题单股原时干 | 目标对象 |
| product.secondary.*、exposure.* | 主题辅助与实际子主题 | 辨别结构，不能重复计票 |

以上为现代金融角色假设。值符不确认政策托底，戊不确认真实流入，开门不确认机构操盘。星门神先读原义，再说明可能的市场表现，不能把象意当新闻。

按月令、符使、星/门/干各层反伏吟看全盘；再逐角色读星门神、天地干顺序、主寄、旺衰、格局、刑空墓迫及适用例外。星旺衰用原盘声明的专表；门干宫不用星表。宫间生克比较谁支持、谁限制、作用在何层，不拼任意同宫五行通关。

同宫角色在`coincident_role_groups`中列出。例如值符与景门同宫只能形成一个相关结构，不能当两份独立利好。见吉格仍保留惊门、门迫、空墓等反证；有利干格不能直接宣布下跌空间封死。

## 3. 基金主题

当前登记主题包括index、ai、software、semiconductor、nonferrous_metals、power_generation、power_equipment、dividend_low_volatility、healthcare、finance、manufacturing；符号和适用范围以配置为准。

- AI保留电子硬件、光通信、软件应用等实际子主题；不能因统计制造业占比最大就与有色共用“制造业”方向。
- 有色区分矿产、冶炼及金属结构。当前兑金/矿产映射是候选方法，不能伪称古籍已验证的证券规则。
- 发电公用事业与电力设备分别绑定；发电不自动随宽基涨跌。
- 红利低波按真实行业权重分析，不直接等同银行，也不承诺低风险。
- 医疗天心/乙为身份映射；天芮并不自动利好创新药。证券开门为身份，不把“吉门”本身重复当涨因。
- 真正相同的主辅结构允许并列。资料无法区分时直说区分能力不足，不临时换用神制造排名。

未知主题的基金只保留市场背景与待核项，不能自动继承指数方向。现有映射不足时另登记方法版本，不在看到行情后临时改表。

## 4. 逐日作用与裁决

保留同一周盘；每一天列实际日柱、流干在原天盘的宫、流支本宫及具体冲合对象。六甲各自遁仪：甲子戊、甲戌己、甲申庚、甲午辛、甲辰壬、甲寅癸。流日旬空与原时旬空分开；本工作流不以流日旬空覆盖原时旬空。

日干/遁仪本身、干落宫、地支本身、支本宫四层五行分开。巳支属火，落巽四宫木；写“巳支本宫巽木生离火”，不能缩成“巳木”。element_layers保留各层，role_relations中的branch_palace_to_target与branch_element_to_target分别表示支宫与支本身，不可互换。day_stem_element_to_target表示日干本身（甲为木），resolved_stem_element_to_target表示遁仪（甲申遁庚金）；兼容字段stem_element_to_target仍表示原日干，不代替遁仪或干宫。

申只填申空，不填酉空；申冲寅，不冲丑。双支宫中一支被冲，不能声称另一支也解。马星、同宫、合、冲、填实是不同条件；不自动把马动解释为解墓解空。程序列几何事实，只有明确绑定的角色限制才计算悬置是否仍在。

例如角色确实受原酉空限制时可填：
`analysis_conditions: {"market.capital":{"void_branch":"酉","evidence":"角色支位及实际作用依据"}}`。
墓限制须给同一角色的已核墓支与采用口径；未核整表不得升级为实际作用。旧role_context只作用旧基线，不自动移植到新角色。

每一天完成以下判断，不规定吉凶票数或统一权重：

1. 主对象的状态、当日作用支持何种方向？
2. 哪些角色提供同向支持，哪些只是波动/参与方式，哪些构成反证？
3. 主辅矛盾怎么裁决？辅助支持是否足以改变方向，还是只能改变强弱、持续性或操作条件？
4. 保留什么成立条件、反转条件、未判问题？哪些需要14:30真实行情确认？

证据够用就给明确偏涨/偏跌；不足则给方向未明并指出原因。相持不表示窄幅。周五不预设跌，不能把某一次周五失误推广为固定规律。

## 5. 日线、分时与量能

分别判断收盘相对前收、隔夜跳空、开盘至收盘、振幅、分时路径、量能、广度与主题相对强弱。收盘涨而开盘至收盘跌可能同时成立。只有日线不能确认“尾盘拉回”；缺上涨家数不能称普涨。

先抑后扬、窄幅、十字星、放量等如要评分，先登记标准与资料口径。程序支持数值阈值判据，阈值是本次研究的声明，不是通用技术定义。例如body_range_pct<=10可以作为某次十字星研究标准，需在发布前说明理由。未登记的模糊句只作定性复核，不事后补阈值算命中。

目前日层不把日干强行解释为上午、日支解释为下午。同盘另加小时层须提前说明方法与时间边界，日层未提供时序依据时给条件窗口，不能报精确分钟高低点。点位或百分比另需技术/历史数据依据，不从宫数、吉格或马星直接换算。

## 6. 生成、完成草稿与发布

复用现有私有Python，无需安装依赖：

```text
<私有Python> scripts/finance_forecast.py --mode multi_role --chart chart.json --request request.json --output context.json --draft draft.json --markdown evidence.md
```

输出context含原盘/请求/方法快照、全盘事实、逐角色结构、日作用、同宫组、主题敞口与独立legacy_baseline。生成证据不等于生成最终预测。

解盘者填写draft每个交易日的direction（up/down/undetermined）、supporting_roles、opposing_roles、rationale、conflict_resolution、conditions、unresolved。角色id须来自本标的context。明确涨跌需有产品主对象、支持证据和成立条件；所有交易日保留，不能删掉难判日。草稿direction初始为null，不能参加预测评分。

可选shape_forecasts示例：

```json
{"id":"small-body","metric":"body_range_pct","basis":"ohlc",
 "operator":"<=","value":10,"reason":"本次事前声明的小实体标准；方向另判"}
```

支持指标及口径见[finance_synthesis.py](../scripts/finance_synthesis.py)的METRICS：same_asset_return为同标的收益；ohlc为日线；minutes为分时；volume和amount分别为同口径成交量与额。日线无法复核的形态保留未判。

```text
<私有Python> scripts/finance_record.py publish --draft draft.json --output forecast-v2.json --markdown answer.md
<私有Python> scripts/finance_record.py validate forecast-v2.json --chart chart.json
```

发布命令记录实际发布时刻，重算时序。开盘后才发布的全天判断不能算完整前瞻，收盘后只能作事后/未来日期分析。声明issued_at、证据created_at、草稿created_at和实际published_at分开。旧记录/草稿不覆盖，修订另存并注明原记录与新事实。

v2核验会复算证据、检查角色引用、判断结构与哈希；显式综合是解盘者的判断，不是程序可机械证明的涨跌算法。本地时间及哈希不构成第三方不可改时间戳。

旧CLI兼容：不带mode或`--mode legacy`继续生成原v1记录；旧记录仍按原快照复算。不得将legacy_baseline情景幅度直接贴给新方向，或手改旧分数。

## 7. 行情采集与事实核验

`finance_observe.py`目前自动采集人民币sh/sz证券价格，保存第三方原始响应与来源；其他市场、基金正式净值和公司公告须另查可靠来源。

请求包含date、mode（intraday/closed）和products数组。每个产品需asset_id、symbol（如sh000001）、expected_name_fragments、metadata_source、currency=CNY、return_basis=price_return、price_tolerance及observation_kind（exact/proxy）。price_tolerance按核对后的报价精度填写，例如指数0.01、三位小数ETF0.001，不能统一用宽容差掩盖ETF冲突。ETF参考基金时用proxy并给reference_for。代码名称先由官方资料核定，采集器不猜目标ETF。

```text
<私有Python> scripts/finance_observe.py --request observation-request.json --output observations.json
```

- 盘中检查请求交易日、名称、代码、时间和报价新鲜度；目前盘中采集是单源快照，交叉核验由直接行情源补充，不宣称已双源确认。
- 收盘模式用日线，核OHLC和日期，比较腾讯/东方财富共同日线及共同分钟。242与241个分时点本身不构成冲突；共同点差异超过价格容差才标争议。
- OHLC计算涨跌、跳空、日内收益、振幅、实体占比、收盘在全日区间的位置与上下影。尾盘净变动用14:30与15:00的采样价；尾盘振幅按14:30—15:00标签的31根分钟高低价定义，缺分钟或只有收价时不生成完整振幅。量能需上一同口径日数据。
- 收盘后报价更新时间不等于新增交易；缺数不写“尾盘已收红”。不同日期、名称错配、来源冲突均保留原因。disputed/rejected/unavailable不能当确认事实。
- ETF价格是代理，不是联接基金当日净值；不可由代理涨幅算实际账户余额、兑现亏损或触发绝对金额风险线。基金净值公布后按实际份额、批次、分红和费用另算。

需要复盘时并排列原句与实际数据，分别评价方向、幅度、分时和主题。局部符合保留，矛盾也明确指出，不用“盘中出现过一次反弹”抹掉收盘方向错误。

## 8. 14:30纠偏与赎回安排

读同一原预测、当前修订和单一订单账。先核当天市场/主题/目标ETF，再核最新正式基金净值日期。行情反向时先检查代码、时刻与口径，再判断推迟、提前、缩量或维持尚未执行的操作，另存修订理由。14:30自动任务由用户授权后设置；技能本身不擅自建任务或下单。

可赎回状态、持有天数、费率分别核。常见七天短赎费率门槛不是统一锁定期；特殊持有期产品按合同实际限制。持有期按申购和赎回确认日及平台规则核到批次，先进先出按份额计算，不以提交日简单相减。比较短赎费用与继续持有风险，不把“等免手续费”当唯一选择。

场外申请为未知价，不能锁住14:30的ETF涨幅。赎回费用约为确认赎回份额×确认净值×适用费率；到账时点另核。优先用平台显示的分批费用和可用份额。

已提交、可撤、已确认、在途和到账分开。计算新动作前对齐持仓口径与订单扣减状态，避免同一笔重复赎回。用户已报操作不能当未操作；未提供确认份额与费用不能编造。现金分红单列，不混入基金余额。

若要求逐步降至目标金额，按目标、已执行/在途订单和实际余额安排每日有条件的份额/金额，周五再以最新信息校正。金额来自用户约束与风险预算，不能声称是奇门算出的最优比例；未知价下不能承诺下周余额精确等于目标，也不能承诺亏损最小、收益最大。不代用户交易。

## 9. 分维度评价

结局单独保存，不能回写预测。用`finance_record.py evaluate`评价同一种方法；v1/v2分别跑。v2只收published记录，筛除development、盘中、事后、采价未核、缺失结局和代理口径。

每条结局含record_sha256、asset_id、date、currency、return_basis、return_pct、available_at、source，可另给observation_kind、metrics和metric_bases。真实NAV没有时不能用ETF代理冒充；代理记录不参加目标基金准确率。完整日结局的可得时刻不能早于采价结束。

报告K（有同口径结局的完整前瞻行）、P（其中明确涨跌行）、C（其中方向正确行）、C/P方向准确率、P/K覆盖率、C/K及缺失/排除数。undetermined不算方向命中，也不自动算窄幅。形态按发布时冻结的各判据单独评分，缺数据单列。

同盘、重叠日期与相关基金不视为独立样本。当前开发案例不作为盲测；未来新样本应在结果前发布与冻结，并对照旧基线及简单基线。程序测试只验证流程和计算，无实际结局时不填真实命中率。扣费经济结果需真实成交账，行情涨跌准确不能替代净收益检验。
